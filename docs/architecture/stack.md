# Technology Stack

Status: Accepted  
Last reviewed: 2026-08-14

## Decision

PayForWhat starts as one browser-first web application in a pnpm monorepo. A tool is a
product module, not a repository, deployment, or subdomain.

| Layer                | Choice                    | Pinned version    |
| -------------------- | ------------------------- | ----------------- |
| Runtime              | Node.js                   | 24.x              |
| Package manager      | pnpm                      | 11.19.0           |
| Monorepo task runner | Turborepo                 | 2.10.9            |
| Web framework        | Next.js App Router        | 16.3.0            |
| UI runtime           | React and React DOM       | 19.2.8            |
| Language             | TypeScript                | 6.0.3             |
| Styling              | Tailwind CSS              | 4.3.3             |
| Runtime contracts    | Zod                       | 4.4.3             |
| Icons                | Phosphor Icons            | 2.1.10            |
| Unit tests           | Vitest                    | 4.1.10            |
| Static analysis      | ESLint and Next.js config | 9.39.5 and 16.3.0 |
| Formatting           | Prettier                  | 3.9.6             |

TypeScript 6 is deliberate. TypeScript 7 is available, but its tooling API and the
current typescript-eslint compatibility range make it premature for this repository.
Reconsider it when the full lint and editor toolchain supports it without running two
compiler generations.

Dependencies are exact-pinned. Renovation should happen through reviewed pull requests
with the full verification command.

The Vercel CLI is an operator tool rather than an application dependency. It stays
outside the workspace dependency graph so the application audit measures shipped and
build code. This setup was verified with `pnpm dlx vercel@59.0.0`; the unrelated older
global executable is not relied upon. Review and deliberately update that pinned
operator version separately from application dependencies. The local repository is
linked to the Vercel project through ignored `.vercel` metadata.

## Initial deployment boundary

`apps/web` is the only initial Vercel project. Public tools use paths:

```text
/en/tools/<slug>
/ko/tools/<slug>
```

The first scaffold is English-only. Add `next-intl` before the first translated route so
locale metadata, canonical URLs, alternate links, and messages share one implementation.
Do not publish machine-translated placeholder pages.

Vercel serves the Next.js shell, static content, and cacheable pages. The browser
performs the actual work whenever practical. GCP is not part of the first feature.

## Tool contract

Every catalog entry declares:

- Stable identifier, locale-independent slug, owner, and lifecycle status
- Supported locales
- Local, server, or hybrid processing
- Whether network access is required
- Data sensitivity
- Server cost class

The build rejects a local tool that declares network access or server cost. This
contract will expand before server-backed tools are accepted.

The router combines a manifest slug with a supported locale. A catalog entry never
stores a locale-specific route, so `image-resizer` resolves independently to
`/en/tools/image-resizer` and `/ko/tools/image-resizer` when those locales are
published. The planned `resume-builder` follows the same contract when it is scheduled.

Tool implementations should separate:

- A pure engine with no React or Next.js dependency
- A narrowly scoped client interface
- An independently useful content page with instructions, examples, limitations, privacy
  behavior, and frequently asked questions
- Tests and representative fixtures

Simple tools stay in the web application until there is a real dependency or runtime
boundary. A large WASM dependency may become a package. A worker that needs FFmpeg, OCR,
queues, or long-running compute may become a separate app, but it can remain in the same
repository.

The first Image Resizer uses a pure local pipeline:

```text
inspect bytes -> decode -> plan geometry -> transform -> encode -> inspect again
```

The implementation uses capability detection rather than filename assumptions and
re-reads generated bytes before reporting success. A dedicated Web Worker owns decoding,
rendering, encoding, and output validation so the interface remains responsive. It loads
and announces readiness when the tool page starts, stays alive for repeat work, and is
terminated on cancellation or unmount to release in-progress resources. The initial
engine uses browser-native image APIs without a codec dependency. Add one only after
comparing browser coverage, output correctness, metadata behavior, bundle size, license
obligations, and cancellation support; this decision does not require GCP or a database.

## Privacy and advertising boundary

Local is the default:

```text
processingMode: "local"
networkAccess: false
serverCostClass: "none"
```

Pages whose DOM contains sensitive user input must not load AdSense or third-party
analytics. Ads belong on public landing pages, guides, and other publisher-content
pages, separated from controls and calls to action.

User-provided values must never appear in URLs, analytics events, application logs, or
error reports.

If a future tool genuinely requires a server, the intended shape is:

```text
Browser
  -> signed Cloud Storage upload
  -> Cloud Tasks
  -> private Cloud Run worker
  -> short-lived result
```

File bytes must not be proxied through a Vercel Function. Server processing requires
explicit user notice, deletion semantics, cost limits, abuse controls, and a separate
privacy review.

## Adoption gates

Add infrastructure only when the product requires it:

- `next-intl` before adding Korean or another locale
- MDX before the guide catalog needs structured, reviewed long-form content
- Playwright before the first interactive tool is released publicly
- IndexedDB when the first versioned local document schema is implemented
- GCP only for work that cannot run acceptably in the browser
- A database only for user-owned mutable state that cannot be local
- Hosted generative AI only after a product demonstrates that it improves the core task
  enough to justify variable inference cost, a new privacy boundary, abuse controls, and
  a usable non-AI fallback

Do not add authentication, Redux, React Query, a CMS, a database, or a UI component
mega-library to the initial platform.

The planned resume builder remains a valid local product without generative AI. Hosted
AI is outside its initial scope because cost and sensitive-data handling require a
separate decision, not because differentiation requires an AI feature.

## Verification contract

The repository-level acceptance command is:

```sh
npm run verify
```

It checks formatting, DCO policy integration, linting, types, unit tests, a production
build, and reviewed license-metadata baselines. It is not a deployment authorization.
The separate `npm run release:verify` command intentionally remains blocked until the
first release pipeline creates and verifies complete legal artifacts.
