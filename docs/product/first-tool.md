# First Tool: Image Resizer

Status: Accepted for implementation  
Last reviewed: 2026-08-14

## Product statement

> Check the requirement. Fix the image locally. Validate the result before download.

The first PayForWhat product helps a user prepare one or more images for a form, portal,
listing, or profile that declares technical upload requirements. The workflow is
deliberately explicit:

1. **Diagnose** the selected file against requirements entered by the user.
2. **Fix** supported dimension, fit, format, file-size, and metadata problems locally.
3. **Revalidate** the generated file itself before offering it for download.

The product does not claim to predict every undocumented rule of a third-party website.
It proves only the constraints the user entered and the properties the browser can
reliably inspect.

The initial route is `/en/tools/image-resizer`.

## Why this is first

- The task is urgent and concrete: a user has a file and a visible requirement to meet.
- The complete supported workflow is deterministic and can run without an account,
  database, hosted AI, or server compute.
- Local processing protects personal photos and avoids recurring per-operation cost.
- Diagnosis and post-conversion validation provide a clearer outcome than an isolated
  compressor, resizer, or format converter.
- The same tested image engine can support future focused workflows without publishing
  duplicate doorway pages or pretending that identical controls are different products.
- Its scope is small enough to test the PayForWhat product, privacy, accessibility, and
  advertising boundaries before taking on a document editor.

The market context is recorded in
[Recurring Subscriptions for One-Time Utility Tasks](../research/recurring-utility-subscriptions.md).
That research informs the opportunity but does not substitute for validation with real
tasks and files.

## Version 1 scope

### Supported input

- One to 20 static JPEG, PNG, or WebP files with the same output settings
- A 25 MB, 40-megapixel, and 8,192-pixel-per-side safety boundary before decode
- A 200 MB total input boundary and a 100 MB generated ZIP boundary for batch work
- File signature, decoded format, pixel dimensions, and byte size inspection
- Detection of metadata classes that the implementation can verify and remove
- A clear report showing which entered constraints pass, fail, or cannot be evaluated

File extensions alone are not trusted. The tool must inspect the file and successfully
decode it before enabling transformation.

### User-entered constraints

- Exact width and height, or maximum width and height
- `cover` for filling exact dimensions with a centered crop
- `contain` for fitting inside exact dimensions with explicit background or transparency
  behavior
- JPEG, PNG, or WebP output
- An optional maximum output size in decimal kilobytes (`1 KB = 1,000 bytes`), with the
  exact byte count shown in the result
- Removal of copied EXIF, XMP, IPTC, and other supported application metadata

Maximum dimensions preserve aspect ratio and never upscale unless the user explicitly
allows it. Exact dimensions require the user to choose `cover` or `contain` whenever the
source aspect ratio differs.

### Generated result

- A new, locally generated file rather than a renamed source file
- A before-and-after report for every declared constraint
- Decoded output dimensions, detected output format, and exact output byte count
- Download only after the generated bytes have been re-read and revalidated
- Direct image download for one input or a local ZIP download for multiple inputs
- A useful explanation when the selected format and constraints cannot all be met

An optional byte limit means **at or below the limit**, not an exact target size. The
tool must not claim that it can produce an exact kilobyte value. Lossless PNG output,
extreme dimensions, a very low byte cap, browser memory limits, or an incompatible
transparency requirement can make a request impossible. In those cases, it must preserve
the source, explain the conflict, and suggest a specific change instead of silently
violating a constraint.

## Explicit exclusions

Version 1 does not support:

- HEIC, HEIF, AVIF, GIF, SVG, TIFF, camera RAW, or unknown formats
- Animated or multi-frame PNG and WebP content, and multi-picture JPEG containers
- Minimum-dimension, DPI, physical-print-size, color-profile, or content-policy checks
- Folders, saved queues, background uploads, or server-generated archives
- Face detection, subject-aware cropping, background removal, OCR, or generative AI
- Upscaling that invents detail
- Server-side conversion or cloud storage
- Remembering files or image contents between sessions
- Reading rules automatically from a third-party upload page

Unsupported, malformed, encrypted, oversized, or undecodable files receive an explicit
non-destructive error. The interface must never imply that changing an extension is a
conversion.

## Product guarantees

- No signup, login, payment, watermark, or PayForWhat branding in the output
- No artificial processing count or output quality limit
- Source and generated image bytes remain in the browser
- Image contents and entered constraints are not placed in URLs, logs, telemetry, or
  error reports
- No copied supported application metadata remains in a successful output
- The downloaded file is the same byte sequence that passed post-generation validation

These statements may be presented to users only after automated and manual verification
proves them for the released build.

## Honest validation boundary

The tool validates declared technical properties, not acceptance by another service. A
correct image may still be rejected because the destination has undocumented rules,
content moderation, account limits, filename rules, stale instructions, or a different
definition of a unit.

The result must therefore say what was verified, for example, "800 x 800 pixels, JPEG,
94,812 bytes; all entered constraints pass." It must not say "guaranteed to upload" or
"accepted by every website."

## Advertising and privacy boundary

The processing route must not load AdSense, third-party analytics, session replay,
third-party support widgets, or other third-party scripts. It contains user-provided
image data and task controls.

Advertising may appear on a separate public landing page or genuinely useful guides.
Those pages must not receive source images, generated images, constraint values, or
object URLs from the processing route. Ads must remain visually and spatially separate
from the control that opens the tool.

## Acceptance gates

### Functional accuracy

- JPEG, PNG, and WebP fixtures are identified by inspected bytes and successful decode,
  not by filename.
- Exact-dimension `cover` output has the requested dimensions and documented crop.
- Exact-dimension `contain` output has the requested dimensions and documented padding
  or transparency behavior.
- Maximum-dimension output stays within both limits and preserves aspect ratio.
- Output signatures, decoded formats, dimensions, and byte counts match the result
  report.
- When a maximum byte constraint succeeds, the generated file is at or below that exact
  byte count.
- Post-generation validation runs against generated bytes, not in-memory assumptions.
- Supported EXIF, XMP, IPTC, location, device, and editing metadata fixtures do not
  survive output.
- Impossible combinations end with a clear explanation and no misleading success state.
- Source bytes remain unchanged after success, cancellation, and failure.
- Batch work runs sequentially, isolates unsupported files, and never offers a ZIP that
  exceeds the documented output boundary.

### Privacy, resilience, and accessibility

- A network test proves that source bytes, generated bytes, thumbnails, filenames, and
  entered constraints never leave the browser.
- The processing route contains no advertising, third-party analytics, or session replay
  requests.
- Cancellation releases object URLs, workers, image bitmaps, canvases, and large
  buffers.
- Corrupt, unsupported, animated, and resource-exhaustion fixtures fail without a page
  crash or partial download.
- The core flow works after the initial page load when the network is unavailable.
- Keyboard-only and screen-reader users can understand the requirement form, comparison
  report, errors, progress, and download state.
- The current and previous major versions of Chrome, Edge, Firefox, and Safari pass the
  core fixture suite.

### Release-blocking kill gates

The first product remains non-indexed and unreleased if any of the following is true:

- Generated files can be offered before their bytes are revalidated.
- A success state can violate an entered dimension, format, or byte constraint.
- A supported metadata fixture survives while the interface claims removal succeeded.
- Image or constraint data reaches a server or third party on the processing route.
- Common impossible requests degrade silently instead of explaining the conflict.
- Supported inputs repeatedly crash or freeze the core flow on the browser test matrix.
- The interface implies exact-size generation or guaranteed acceptance by another site.

Product expansion also stops if task observation shows that users cannot translate real
upload instructions into the constraint form. In that case, improve requirement entry
and explanations before adding formats or additional image tools.

## Implementation sequence

1. Define the versioned requirement, diagnosis, transformation, and result contracts.
2. Build byte-signature inspection and static JPEG, PNG, and WebP decode fixtures.
3. Implement exact and maximum dimension planning with tested `cover` and `contain`
   geometry.
4. Implement local re-encoding, metadata stripping, cancellation, and resource cleanup;
   warm the worker before a file is selected so an already loaded page can finish a task
   without the network.
5. Add bounded quality search for optional maximum bytes and explicit impossible-result
   reporting.
6. Re-read generated bytes and build the before-and-after constraint report.
7. Complete offline, accessibility, browser, privacy, corruption, and resource tests.
8. Publish only after every release-blocking gate passes.

The processing route remains absent from the sitemap and non-indexed until the complete
core flow meets these criteria.
